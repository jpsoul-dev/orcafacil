# Checklist de Qualidade — Gate Final Antes de Salvar

Rode este checklist mentalmente sobre o documento pronto, antes de escrever o arquivo (Etapa 6). Se qualquer item
falhar, corrija o texto antes de salvar — não salve e corrija depois.

## 1. Ausência de detalhe técnico

- [ ] Nenhuma menção a tabelas, colunas, schemas, endpoints, bibliotecas, frameworks ou linguagens
- [ ] Nenhuma decisão de arquitetura ou implementação ("criar uma tabela", "usar webhook", "cachear isso")
- [ ] Nenhuma estimativa de esforço/tempo de desenvolvimento
- [ ] Nomes de telas/funcionalidades usados são os que o usuário final vê (linguagem de produto), não nomes
      internos de componentes de código

## 2. Ausência de ambiguidade

- [ ] Todo campo do template está preenchido com informação real — nenhum "a definir" ou placeholder genérico
- [ ] Toda seção que foi genuinamente inaplicável diz "Não aplicável" explicitamente, em vez de estar ausente
      sem explicação
- [ ] Nenhum adjetivo vago sem referência concreta ("melhor", "mais rápido", "mais intuitivo") sem um número,
      exemplo ou comparação que dê significado a ele
- [ ] Os Critérios de Aceite (ou o Comportamento Esperado, no caso de bug) são verificáveis objetivamente — uma
      pessoa de fora conseguiria checar se cada um foi cumprido, sem precisar perguntar ao autor o que ele quis
      dizer

## 3. Objetividade

- [ ] Nenhuma frase repete a mesma informação com palavras diferentes em seções diferentes
- [ ] O documento é o mais curto possível sem perder informação necessária — sem enchimento
- [ ] Contexto/Motivação explica o *porquê* de forma que qualquer pessoa do time entenda a relevância sem
      conhecimento prévio da conversa

## 4. Fidelidade ao que o stakeholder pediu

- [ ] Nenhuma informação foi inventada ou assumida além do que foi dito no rascunho ou nas respostas da
      entrevista
- [ ] O documento reflete exatamente a prioridade, urgência e escopo que o stakeholder indicou — nem mais, nem
      menos
- [ ] Se alguma informação ficou genuinamente indisponível mesmo após a entrevista (ex: stakeholder não sabe a
      frequência exata de um bug), isso está registrado como tal no texto, não omitido silenciosamente

Se qualquer item deste checklist falhar e a correção depender de informação que você não tem, volte para a
Etapa 4 (Entrevista) e pergunte — não corrija "adivinhando".
